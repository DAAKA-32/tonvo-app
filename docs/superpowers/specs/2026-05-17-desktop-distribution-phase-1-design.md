# Cue Desktop — Phase 1: Shell + Direct Download

**Status:** Draft for review
**Date:** 2026-05-17
**Owner:** Emilien Nepveu
**Scope:** Phase 1 only. Phases 2–7 are outlined as an appendix for context, but each gets its own spec when it lands.

---

## 1. Goal

Ship a cross-platform installable desktop application of Cue (Tonvo) that:

1. Users download directly from `tonvo.com` with an OS-detected CTA.
2. Installs natively on Windows (`.exe`), macOS (`.dmg`), and Linux (`AppImage` + `.deb`).
3. Launches as a real native window and presents the existing Cue web product.
4. Survives short network drops with an offline shell (login screen + reconnect logic).
5. Auto-updates from a release manifest hosted by Cue's existing Vercel deployment.

Phase 1 explicitly does **not** include: native audio capture, keychain-backed auth, native tray, native Stripe flow, sync, crash reporting, or code signing. Those are Phases 2–7.

## 2. Non-goals

- **App Store distribution.** Explicit hard "no" in the source spec.
- **Rewriting the web app.** The Next.js app stays unchanged except for two additions: a download hero block and a release-manifest API route.
- **Signed binaries in Phase 1.** Decision recorded: ship unsigned dev builds for Phase 1; revisit signing before public launch. Windows users will see SmartScreen; macOS users will see "unidentified developer" — both acceptable for a closed beta cohort.
- **In-app payments.** Stripe stays on web. Desktop opens system browser for upgrade flows (Phase 5 will formalize this).

## 3. Architecture

### 3.2 Runtime model — "hybrid load"

On launch, the Tauri shell:

1. Renders `src/index.html` (offline shell) immediately — gives instant feedback (<200ms to first paint).
2. Pings `https://app.tonvo.com/api/health` with a 1.5s timeout.
3. If reachable, navigates the webview to `https://app.tonvo.com`. The user sees the live web app, including all current auth/session/dashboard pages.
4. If unreachable, keeps the offline shell visible with: "Cue is offline. Reconnecting…" + retry button + last-cached session timestamp.

The webview itself is the OS-native one (WebView2 on Windows, WKWebView on macOS, WebKitGTK on Linux). Tauri does not bundle Chromium — that's where the size savings come from.

### 3.3 Auto-update flow

Tauri's `tauri-plugin-updater` polls a JSON manifest at:

```
https://app.tonvo.com/api/desktop-release/{platform}
```

Where `{platform}` is one of `windows-x86_64`, `darwin-aarch64`, `darwin-x86_64`, `linux-x86_64`. The route returns:

```json
{
  "version": "0.1.3",
  "notes": "Bug fixes and performance improvements.",
  "pub_date": "2026-05-20T12:00:00Z",
  "platforms": {
    "windows-x86_64": {
      "signature": "...",
      "url": "https://github.com/tonvo/cue-desktop/releases/download/v0.1.3/Cue_0.1.3_x64_en-US.msi.zip"
    },
    "darwin-aarch64": { "...": "..." }
  }
}
```

The manifest is generated by the GitHub Actions release workflow (Section 5) and committed back as `public/desktop-releases/latest.json`. The Next.js route reads that file and returns the slice for the requested platform.

For Phase 1, binaries are **not OS-signed** (no Apple Developer ID, no Windows EV cert). However, Tauri's updater requires a minisign keypair for its own update-bundle verification — this is generated once via `npx tauri signer generate`, takes 30 seconds, and is unrelated to OS-level signing. The public key lives in `tauri.conf.json`; the private key + its password live in GitHub Actions secrets (`TAURI_SIGNING_PRIVATE_KEY`, `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`). Phase 7 adds the real OS-level signing (Apple Developer ID + Windows EV) on top.

### 3.4 Landing-page download UX

`src/app/page.tsx` gets a new hero CTA block (positioned below the existing cinematic hero per recent commit `9f509ce`):

- Client component sniffs `navigator.userAgent` + `navigator.userAgentData` to pick a default OS.
- Big primary button: **"Download Cue for {detected OS}"** linking to the matching GitHub release asset URL.
- Secondary text links: "Windows · macOS · Linux" for users on a different OS.
- Fallback if detection fails: shows all three side by side.

The download asset URLs follow the convention:
- `https://github.com/{org}/cue-desktop/releases/latest/download/Cue-Setup.exe`
- `https://github.com/{org}/cue-desktop/releases/latest/download/Cue.dmg`
- `https://github.com/{org}/cue-desktop/releases/latest/download/Cue.AppImage`
- `https://github.com/{org}/cue-desktop/releases/latest/download/cue_amd64.deb`

These are stable URLs — GitHub redirects `latest/download` to the most recent release.

## 4. Components in detail

### 4.1 `desktop/src-tauri/tauri.conf.json`

Drives the bundle:

- `productName`: `"Cue"`
- `identifier`: `"com.tonvo.cue"` (also the macOS bundle ID and Windows app ID)
- `bundle.targets`: `["nsis", "dmg", "appimage", "deb"]`
- `bundle.icon`: per-OS icons in `src-tauri/icons/`
- `window`: 1280×800 default, min 960×600, resizable, with native title bar
- `plugins.updater.endpoints`: array containing the Vercel manifest URL above
- `plugins.updater.dialog`: true (Tauri shows a "Restart to update" prompt)
- `app.security.csp`: explicit allow-list for `https://app.tonvo.com` + Stripe + Supabase + Firebase domains
- `app.withGlobalTauri`: false (no API leak to the remote web app)

### 4.2 `desktop/src-tauri/src/main.rs`

Responsibilities, kept tight:

- Single-instance guard (prevents two windows on second launch — uses `tauri-plugin-single-instance`).
- Deep-link registration for `cue://` URI (placeholder; used in Phase 2 for OAuth callback).
- Updater initialization.
- Builds main window, points it at the bundled `index.html`.

No business logic. The Rust side is intentionally minimal in Phase 1.

### 4.3 `desktop/src/shell.ts`

The decision logic:

```ts
const TARGET = "https://app.tonvo.com";
const HEALTH = `${TARGET}/api/health`;
const TIMEOUT_MS = 1500;

async function probe(): Promise<boolean> {
  const ctrl = new AbortController();
  const t = setTimeout(() => ctrl.abort(), TIMEOUT_MS);
  try {
    const r = await fetch(HEALTH, { signal: ctrl.signal, cache: "no-store" });
    return r.ok;
  } catch { return false; }
  finally { clearTimeout(t); }
}

async function boot() {
  if (await probe()) {
    window.location.replace(TARGET);
  } else {
    document.body.dataset.state = "offline";
    setTimeout(boot, 3000); // exponential backoff in actual impl
  }
}
boot();
```

The offline shell is plain HTML/CSS in the same file — Cue branding, "Reconnecting…" copy, retry button. Total bundle for `desktop/dist/` < 30 KB.

### 4.4 `src/app/api/desktop-release/[platform]/route.ts`

```ts
import { NextRequest, NextResponse } from "next/server";
import manifest from "@/../public/desktop-releases/latest.json";

const PLATFORMS = new Set([
  "windows-x86_64", "darwin-aarch64", "darwin-x86_64", "linux-x86_64",
]);

export async function GET(_: NextRequest, { params }: { params: { platform: string } }) {
  if (!PLATFORMS.has(params.platform)) {
    return NextResponse.json({ error: "unknown platform" }, { status: 404 });
  }
  const entry = manifest.platforms[params.platform];
  if (!entry) {
    return NextResponse.json({ error: "no release for platform" }, { status: 404 });
  }
  return NextResponse.json({
    version: manifest.version,
    notes: manifest.notes,
    pub_date: manifest.pub_date,
    url: entry.url,
    signature: entry.signature ?? "",
  });
}
```

Static file → static response, no DB hit. The manifest gets refreshed by the release workflow committing `public/desktop-releases/latest.json` back to `master`.

## 5. CI/CD — `desktop-release.yml`

Triggered on `git tag desktop-v*`. Matrix:

| OS runner | Output |
|---|---|
| `windows-latest` | `Cue-Setup.exe` (NSIS) |
| `macos-14` (Apple Silicon) | `Cue.dmg` (aarch64) |
| `macos-13` (Intel) | `Cue.dmg` (x86_64) |
| `ubuntu-22.04` | `Cue.AppImage` + `cue_amd64.deb` |

Job steps per OS:
1. Checkout
2. Setup Rust + Node
3. `cd desktop && npm ci`
4. `npm run tauri build`
5. Upload artifact

Final job:
1. Download all artifacts
2. Create GitHub Release with all binaries
3. Generate `latest.json` manifest from artifact URLs
4. Commit `public/desktop-releases/latest.json` back to `master` (uses a PAT or workflow token with `contents: write`)

Vercel auto-deploys on the commit → updater manifest is live within ~60s of release publication.

## 7. Testing approach

Phase 1 is small enough that automated tests are scoped tightly:

- **Manual smoke checklist** in `desktop/TESTING.md`: install on each OS, launch, observe remote-load, kill network, observe offline shell, restore network, observe auto-recovery.
- **`/api/desktop-release/[platform]` route**: Jest/Vitest unit test verifying 200/404 paths and shape of response.
- **`detect-os.ts`**: unit test with hard-coded UA strings (Chrome/Win, Safari/Mac, Firefox/Linux, mobile).
- **CI build verification**: the matrix workflow itself is the integration test — if any OS fails to build, the release is blocked.

No Playwright/Selenium for the Tauri shell in Phase 1 — Tauri's WebDriver story is still rough and Phase 1 has almost no shell logic to drive.

## 8. Open risks / accepted trade-offs

| Risk | Mitigation | Acceptance |
|---|---|---|
| Unsigned binaries trigger SmartScreen/Gatekeeper warnings | Document in install instructions; closed beta cohort | Accepted for Phase 1 |
| Webview2 may be missing on older Windows 10 | Tauri bundles Webview2 bootstrapper in NSIS installer | Mitigated |
| `https://app.tonvo.com` outage = desktop offline shell only | Phase 4 adds local cache; Phase 1 just shows reconnect screen | Accepted |
| Auto-update signature is unverified | Phase 7 adds proper minisign keypair | Accepted, low risk in closed beta |
| User mistakes desktop window for a browser tab | Custom title bar with Cue branding + locked navigation (no URL bar) | Mitigated |

## 9. Success criteria

Phase 1 is done when:

1. A non-technical user on each of Windows 11, macOS 14, Ubuntu 22.04 can: visit `tonvo.com`, click download, install, launch, log in, complete a session — all without manual steps beyond clicking through OS install warnings.
2. Releasing a new version is one command: `git tag desktop-v0.1.x && git push --tags`. Within 10 minutes, all three OS binaries are on GitHub Releases, the manifest is live, and installed apps prompt for update on next launch.
3. The desktop app launches in <2s on a mid-range machine (Tauri shell + remote nav).
4. Total installed footprint is <50 MB on Windows, <30 MB on macOS, <30 MB on Linux.

## Appendix A — Phase roadmap (context only; each phase gets its own spec)

- **Phase 2** — Native auth + OS keychain token storage + deep-link OAuth.
- **Phase 3** — Native audio capture (replace `getUserMedia`), tray icon, global hotkey, system notifications.
- **Phase 4** — Local session cache, offline replay queue, sync conflict resolution.
- **Phase 5** — Desktop-aware Stripe checkout (system browser + deep-link return, license cache).
- **Phase 6** — Sentry crash reporting + anonymous usage analytics + log forwarding.
- **Phase 7** — Code signing (Win EV cert + Apple Developer ID + notarization), signed auto-updates, optional Linux GPG-signed apt repo.

These are deliberately separate. Mixing them with Phase 1 = a 6-month project before anyone can install the app. Phase 1 = ~1–2 weeks of focused work and yields a real installable product.
